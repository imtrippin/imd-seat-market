# Review history

A sanitized summary of the review chain behind this project, so the repository is self-contained. The full reports, raw review-run records, source snapshots and screenshots are kept outside the repository, unchanged. The JavaScript simulation that the first three sections describe, together with its tests and review artefacts, was removed from the tree on 2026-09-29 and remains in git history. Dates are 2026-09-28 and times are UTC unless stated.

## Who did what

- **Codex** built the simulation's v0.1 (work-receipt model), v0.2 (collateral and arrival-time model) and v0.3 (per-period accounting, owner acknowledgment, draft contract specification) and wrote the responses; it later reviewed each contract version.
- **Claude (Fable 5.1)** reviewed each simulation version (two static reviews of v0.1's three source files with tools disabled, a workspace review of v0.1's trust model against public chain and worker evidence, a static collateral review plus a workspace review of v0.2 with a fuzz campaign, and a bounded static review of v0.3), then wrote the contracts and answered each contract review.

Each item below says which kind of evidence supports it.

## v0.1 and the trust-model review

- **Verified from public chain data.** IMD reward payments reach the NFT holder wallet from IMD's Disperse contract, one share per active agent: the three payouts observed between 2026-09-23 and 2026-09-28 paid about 7.7, 3.05 and 3.12 IMD per agent. The first was one aggregated transfer per wallet; the later two were one transfer per agent.
- **Reported by the IMD developer in on-chain notes, quoted.** "airdropped half of the token rewards to NFTs that performed tasks and run the daemon over the past 48 hours … around 7 imd to each agent" (09-23); "half to ppl with currently active nodes" (09-25); "sent the LP token rewards to workers and stakers" (09-28).
- **Adopted by the prototype.** The owner wallet receives every reward, so the provider is the trusting party. Because one payout aggregated per wallet, v1 requires one hosted NFT per dedicated receiving wallet.
- **Read from the pinned worker release (code inspection, not a live test).** The worker labels an enrollment `stale` with "the NFT moved to another wallet; run `imd start` to pair again", and `nft_transferred` is in its terminal-disconnect set. An NFT transfer therefore ends a hosted device's authority without the host's cooperation. Still untested live: whether the ERC-8004 agent id follows the token, and whether moving the token back revives the old enrollment.
- **Reported second-hand (2026-09-28).** The developer said a sold NFT stops work and task acceptance, with the server disconnecting roughly 30 minutes later. The timing has not been measured independently.
- **Documented by the public IMD API.** Pairing needs the seat holder wallet's EIP-712 signature; the only documented revoke is signed by the device itself; per-launch allocations and wallet earnings exist as records; no payout contract or claim route is documented.
- **Unsent asks for IMD.** A lockable per-seat payout address; EIP-1271 signature support at pairing so a vault could hold the NFT; a wallet-signed enrollment revoke.

## The contracts (2026-09-28)

- **Decision.** The owner chose a rental with a security deposit over the simulation's floor-and-acknowledgment rule: listings set a daily fee, a reward-share percentage and a deposit, any of the first two may be zero, and the parties choose the numbers. `SeatEscrow` implements exactly that. A first floor-and-acknowledgment contract was built and reviewed the same day and then replaced; the git history was rebuilt, so its commits no longer exist.
- **Escrow reviews.** Codex, first review (floor model): two medium findings, fixed the same day; its probes that still apply live in `contracts/test/SeatEscrowReviewProbes.t.sol`. Codex, second review (rental model): a recipient-tax token could short-pay claims and refunds (fixed: `_pushExact` checks the recipient side), two amount paths bypassed the 2^128 claim cap (fixed), a tautological invariant (replaced), plus documentation and deploy-guard items; its reproductions became `contracts/test/SeatEscrowV2Probes.t.sol`. Rehearsed three times on Base Sepolia against mocks with a scripted, asserting walkthrough.

## SeatVault reviews (2026-09-28)

- **Round one (Codex).** Custody could strand the seat after a plain transfer and a provider `end()` (fixed: withdrawal relies on actual ownership and works after `end`); an unreadable or huge reward-token balance blocked withdrawal (fixed); approvals survived device changes and several coexisted (fixed: one active approval, cleared on device change, revoke, end and withdraw); a safe-minting registry could not deliver its agent token (fixed); operator key distinctness; pairing-script expiry recomputation and walkthrough guards (fixed). Reproductions: `contracts/test/SeatVaultReviewProbes.t.sol`, `test/pair-vault.test.mjs`.
- **Round two (Codex).** Malformed `balanceOf` return data still trapped the seat (fixed: withdrawal makes no call to the reward token at all); the walkthrough could execute one call twice by rebuilding with a fresh nonce (fixed: one signed transaction per call, same-bytes retries only, never rebuilt, receipt status required; every step asserts); the pairing script ignored IMD's code expiry and accepted fractional TTLs (fixed). Reproductions: `contracts/test/SeatVaultV2Probes.t.sol` and six more script tests. Codex also verified from the mainnet registry implementation that a contract caller is accepted for ERC-8004 registration.
- **Round three (Codex).** Three low script findings: a failed `cast nonce` read could continue as nonce zero, a status-1 receipt for another transaction hash was accepted, and token-id validation did not enforce the uint256 bound or the string transport type. All fixed the same day; Codex's regressions are kept under `test/codex/` and `contracts/test/codex/`, and the receipt and nonce fixes also have tracked tests in `test/pair-vault.test.mjs`. A second adversarial reviewer confirmed the three closed and added three low items (receipts must carry a block number; canonical decimal token ids; tracked regressions), applied the same day.
- **Verified locally after round three.** 67 Node tests, the 28-check self-test, the 12 round-three probes, 85 Foundry tests across 8 suites, `forge fmt --check` clean.

## Vault-only decision (2026-09-29)

The owner chose the simplest possible product with the fewest ways to be exploited: the vault alone. A listing's only number is the host's percentage; there is no fee and no deposit. `SeatEscrow` (the rental with a security deposit) and its four suites, the escrow deployment script and the vault's informational `escrowAgreementId` field were removed from the tree the same day; the escrow's review history above stays as the record, and the code is in git history should a fee-based listing ever be wanted again. What the host gives up without it is stated in `contracts/VAULT-DESIGN.md`: no guaranteed income, and no protection against an owner who withdraws right before a payout. The escrow was also the one design that needed nothing from IMD; the vault depends on IMD accepting a contract holder at pairing and paying a contract holder, which remain unverified.

## IMD swarm review (2026-09-29, job 11c42a8c)

The first paid review by the IMD swarm, ordered by the owner against commit `a51f9130` with the `audit-imported-code` skill (created 15:22 UTC, completed 15:34 UTC). The network assigned the single review node to one of the owner's own seats (token 2, a Claude worker): an isolated run of the model with no knowledge of this project's sessions, but not a review by a third party. It read every file in scope, ran the suites (48 Foundry, 26 script) and returned 10 findings: one medium (a claim naming the seat collection or the registry as `token` could move a seat on a collection with a legacy `transfer(address,uint256)`; the pinned IMD collection has no such function), four low (a provider could `end()` a fresh vault before the seat arrived; the pairing helper treated millisecond timestamps as seconds; claims were all-or-nothing under a shortfall; `registerAgent` forwarded any calldata) and five informational (no role rotation; the round-three Node probes required `REVIEW_PYTHON`; no invariant suite and a list of untested edges; lint warnings; key handling in the rehearsal script).

Fixed the same day: `settle`/`claim` refuse the seat collection and the registry, `rescueERC721` refuses the reward token and the zero address, `withdrawNFT` refuses the zero address; the provider can end only once the seat is in the vault; `claim` pays what the vault holds and keeps the rest allocated; `registerAgent` forwards only the three `register` selectors; millisecond timestamps are recognised; both Node suites resolve a Python interpreter themselves; the lint sites use `vm.getChainId`/`vm.getBlockTimestamp`; the rehearsal script prefers `python3` and no longer treats a plain "underpriced" reply as a broadcast. Accepted as documented design: no role rotation (the owner address must be a wallet the owner can always control). Deferred: keystore-based signing in the testnet rehearsal script. Regressions and the requested invariant suite: `contracts/test/SeatVaultSwarmProbes.t.sol` and `contracts/test/SeatVaultInvariants.t.sol` (59 Foundry tests across 6 suites).

## Codex's review of the swarm fixes (2026-09-29)

Codex re-reviewed `fcf95097`: no new custody or accounting defect; every swarm finding confirmed closed at the reported boundary. One low test-harness defect: the invariant handler's re-deposit action evaluated a getter after `vm.prank`, which consumed the impersonation, so that path reverted every time and the campaign, which tolerated reverts, never exercised it (546 of 596 calls). Fixed by caching the token id before the prank in every handler action, adding a deterministic regression (withdraw, re-deposit, withdraw), and making unexpected reverts fail the campaign. Codex also noted that the rehearsal script could pick a present but broken `python3` ahead of a working `python`; it now uses the first interpreter that actually runs. Its wider caveats stand: the registry allowlist pins selectors, not implementation semantics; partial claims improve recoverability, not fairness under hostile tokens; a second paid review may again be assigned to one of the owner's seats, since the network's routing is not ours to steer.

## Registration path established (2026-09-29)

Asked whether the developer questions could be answered without asking, the public data settled two of them. `GET /agents/register-intent` (public) returns the exact registration calldata: it targets IMD's registrar `Adapter8004` (proxy `0xde152AfB…`, verified source), not the ERC-8004 registry directly, with `register(uint8,address,uint256,string)`, a function the previous allowlist did not know, so the vault as it stood would have refused IMD's real registration. The registrar requires the caller to be the seat's current owner, keeps the agent NFT itself, binds the agent to the seat and derives control from the seat's owner from then on, and is not payable. The vault now pins the registrar, allows only its two `register` functions and only calldata naming its own seat, and the fork rehearsal registers through it against the real contract and checks that control follows the seat on withdrawal. The registrar mock in the tests behaves the same way. Also from public data: 143 seat holders have code, but 141 are EIP-7702 delegated accounts that still sign as EOAs, and the two real contracts holding seats (59 seats between them) have never paired, so the network offers no evidence yet about ERC-1271 pairing; 35 of 248 payout recipients have code, so the distributor does pay code-bearing holders.

## Codex registrar review (2026-09-29)

Codex reviewed `7d4c1ac3` with twelve probes of its own that run the saved, verified registrar runtime behind a local ERC-1967 proxy (runtime SHA-256 `503f407c…`, matching the public implementation byte for byte). No custody, allocation or own-seat bypass. Three low findings, all applied: (1) the docs said a registrar upgrade always fails closed, but a replacement implementation can accept the old selectors through a bare fallback or change what they do, so the vault now requires the registrar to return the agent id (an empty answer is refused, and the event records the id), and the docs describe the registrar as an external dependency whose reviewed behaviour is not a vault guarantee; (2) stale "registry" wording where the code refuses or calls the registrar; (3) the registrar mock accepted the reserved binding metadata key and could not model a failure after the agent was minted, so it now refuses that key, records and clears the agent wallet, and can fail downstream, with tests for both and for the bare-fallback case. Codex's probes also showed that non-canonical dynamic encodings can yield an empty URI without changing the checked seat, that repeating the registration creates another agent (no uniqueness rule), and that repointing the registrar's registry does not migrate existing agents.

## Third IMD swarm review (2026-09-29, job be59ed06)

Ordered by the owner against commit `c786f66d` through IMD's `audit` template: four specialists (economics, flow, math, permissions) and a judge. Three specialists and the judge ran on seats outside the owner's fleet; the permissions node landed on one of the owner's own seats again. The first judge attempt, a Codex worker, was refused by its provider's safety filter ("flagged for possible cybersecurity risk"), and a Claude worker completed the judgement on the second attempt. The flow and math specialists found nothing (the math one probed registrar replies of 0/1/31/33/64 bytes, dirty head words, truncated calldata, foreign seat ids, corrupt offsets, reserved metadata, and owner claims at 0, 1, 3000, 9999 and 10000 bps). The economics and permissions specialists produced seven findings that the judge re-ran and confirmed, none above low:

- **Low.** A stray ERC-721 with a legacy `transfer(address,uint256)` could be moved by a `claim` on it (an NFT `balanceOf` is a count; the transfer moves the token whose id equals the amount); only the seat collection and the registrar were refused. **Low.** A token reachable through two addresses (an alias or proxy entry point) was split twice, letting the first claimant take the other party's share. Both fixed by one rule: only the pinned reward token is ever settled or claimed (no token parameter, one ledger), and anything else that lands in the vault is the owner's to take back (`rescueERC20`, which refuses the reward token, the seat collection and the registrar, next to `rescueERC721`). The host therefore has no share in any token but the reward token; the earlier any-ERC-20 rule was a design choice, not a requirement.
- **Low.** The provider could `end()` between a plain transfer in and `syncHeld`, closing a vault that never started (the first swarm fix gated on ownership, not on the recorded seat). Now gated on `held`.
- **Info.** Replacing an approval emitted no `PairingCleared` for the old digest (now it does). **Info.** `OtherNFTReceived` could be emitted by anyone calling the hook, and `syncHeld` emitted `NFTDeposited(owner)` (event dropped; `NFTSynced` added). **Info.** The docs called `registerAgent` the only owner-supplied call (the rescues are named now). **Info.** The invariant campaign could not fail its custody invariant and exercised neither pairing, registration, rescue, sync nor a second token (rewritten: the campaign starts with the seat in the owner's wallet, runs both deposit paths, pairing approvals with real operator signatures, expiry, device changes, registration, stray NFTs and a second ERC-20 with their rescues, withdrawals to a third address, and a "strangers" action that asserts every forbidden call fails; invariants tie the seat to a shadow model, `held` to actual ownership, an approval to custody, and a valid signature answer to custody, the approved digest and an unexpired window).
- Also from the judge: a registrar fallback returning one zero word was accepted as agent id 0; the vault now refuses a zero id (still a shape check).
- Codex reviewed the fixes and found one conditional low left: a second entry point of the reward token (an alias or a proxy the token trusts) could be named in `rescueERC20`, and the vault's own call through it moved the whole reward balance to the owner, taking the host's share. Both rescues now snapshot the reward balance and the seat's custody and revert if either changed; `rescueERC721` refuses the registrar as the docs already said; the request generator no longer describes the removed multi-token rule and the gas estimate is current.

## Back to the basic product (2026-09-29, evening)

The owner stopped the growth: "strip all the extra, start with just the basic contract; I wanted a very simple way for people with an NFT to click a button or two and get a worker hosted." Claude wrote the cut as a brief, Codex agreed with corrections (four owner transactions, three when an agent can be reused; a direct safe transfer instead of approve + deposit; registration only when no usable agent exists; keep the safety checks and a tiny recovery record; no coordination server; the same page serves both parties' claims, also after exit). The console, the setup room, scheduling, readiness, the arming screen and the browser rehearsal were removed from the tree (history keeps them). What remains: `host/`, the host helper (offer, pair, resume, status) with the shared library and the offline end-to-end tests (a restart mid-attempt and an agent-reuse agreement included), and `page/`, one static agreement page built from that library with a pinned bundler, no backend, reading the vault through the wallet and IMD's open swarm listing. Handoff between host and owner is two pasted strings and the vault address.

## Mainnet fork rehearsal (2026-09-29)

Prompted by the owner's concern about depositing a real seat: `contracts/test/fork/MainnetFork.t.sol` runs the vault against the real IMD seat collection, the real IMD token and the real ERC-8004 registry on a mainnet fork, impersonating the seat's wallet with a spare seat. ## Setup room and prepared-host mode (2026-09-29)

Codex added a separate keyless setup-room service, scoped wallet sign-in, mutually confirmed appointments, expiring readiness, automatic pairing-offer handoff, two expiry countdowns, silent in-page reminders and calendar export. Optional host automation handles one attempt for an explicitly selected vault using the local operator key, after owner readiness and the matching on-chain approval. Tests cover two independent consoles against local Anvil/fake IMD and the coordination boundaries. No contract changes, public service deployment, real pairing or worker changes. These changes are not a live integration signoff. Claude reviewed them the same evening: the room had become mandatory for starting a pairing (the manual offer-string path could no longer start; fixed, both paths tested end to end), approval hashes were tracked only through the room (now tracked by the console itself and pruned on receipt), and two limits were documented (a contract-wallet owner cannot join a room; behind a proxy the sign-in rate limit shares one bucket). The rest held: the room carries only public data, the consoles reconstruct the sign-in text and re-validate every offer against the vault, unattended signing is limited to a digest the owner already approved on chain, and cancellation is checked immediately before the completion is posted. Codex re-checked the fixes and found two gaps, closed the same evening: the page still disabled the host's start button outside a room (the room now gates it only while signed in, and a manual start shows the copyable offer), and re-importing an offer dropped the record of an unconfirmed approval (unresolved approvals now live in a per-vault ledger apart from the offer state, pruned only on receipt; the end-to-end test holds an approval unmined and proves no new code is requested until it resolves).

## What none of this establishes

These reviews and local tests do not constitute a production audit or establish live IMD compatibility. The reward figures above are three dated distributions, not an income schedule. Mock rehearsals on a testnet prove the scripted lifecycle, not acceptance by IMD or its payout routing.
